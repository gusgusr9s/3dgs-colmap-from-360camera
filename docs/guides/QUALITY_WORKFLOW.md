# ตรวจภาพและสร้าง Model ให้ง่ายขึ้น

## ใช้งานปกติ

1. อัปโหลด Source แล้วสร้าง Views หรือเลือกสร้าง Model อัตโนมัติได้เหมือนเดิม
2. กดสร้าง Model ระบบจัดคิวให้ งานหนักทำทีละรายการทั้ง Views, COLMAP, Mask และ Train เพื่อไม่แย่ง GPU กัน
3. ระหว่างรอมีสถานะลำดับคิวและปุ่ม **ยกเลิกรอคิว** ปุ่มนี้ใช้เฉพาะงานที่ยังไม่เริ่ม
4. ระบบตรวจภาพจากตำแหน่งที่ไม่ได้ใช้เทรน Gaussian ก่อนเผยแพร่ Model

## เมื่อต้องการตรวจหรือเพิ่มรายละเอียด

จากปุ่มสร้าง Model หรือหน้า Camera Preview เปิด **ตรวจภาพ / Mask ก่อนสร้าง Model** (`/prepare/<job>`)

- เริ่มด้วย **ใช้ Views ปัจจุบัน** ได้ทันที
- **PNG 2048** ฉายภาพใหม่จากเฟรมวิดีโอ 360 ต้นฉบับตรงตามมุมเดิม เก็บ PNG และปรับ intrinsics ตามขนาดใหม่ ไม่ใช่การขยาย JPEG เดิม ต้องมี Source เดิมและใช้พื้นที่/เวลาเพิ่ม
- เลือก **ปกติ / เก็บพื้นเพิ่ม / เก็บพื้นทั้งหมด** สีแดงเป็นแนวพื้นที่ล่างที่จะข้าม ส่วน Mask คนคำนวณด้วยโมเดลเดิมตอนเตรียมข้อมูล
- ถ้ามี Mask จริงเดิมแล้ว จะมีลิงก์เปิดดูบนภาพแยกจากภาพจำลองแนวพื้น
- การคัดภาพตรวจรายละเอียดจากมุมหลักของแต่ละตำแหน่ง ข้ามเฉพาะภาพที่ต่ำกว่าค่ากลางมาก เก็บจุดต้น/ปลายและตำแหน่งทดสอบ จำกัดจำนวนที่ตัด และไม่ทำให้ช่องว่างเวลามากกว่า 0.3 วินาที ผนังเรียบอาจมีคะแนนต่ำ จึงปิดตัวเลือกนี้ได้
- แต่ละรอบใช้ชุดภาพของตัวเอง การแก้ PNG, Mask และ JSON ใช้การแทนไฟล์ใหม่เพื่อไม่เขียนทับ hardlink ของรุ่นก่อน

## ตรวจผล

เปิด **ตรวจภาพ Render** เลือกมุมเดียว แล้ว:

- สลับภาพอ้างอิงระหว่างภาพอ้างอิงที่เตรียมไว้กับภาพฉายจากวิดีโอ 360 ต้นฉบับ
- ใช้ภาพคู่ ซูม 150% / 200% และเลื่อนภาพพร้อมกัน หรือใช้แถบลากเทียบ
- ดูเปอร์เซ็นต์พื้นที่ที่ใช้ประเมิน หาก Mask ทั้งภาพจะแสดงว่าไม่มีคะแนน
- เปิด **PLY เต็ม** หรือ **รุ่นโหลดเร็ว** ที่ตำแหน่ง ทิศ FOV และอัตราส่วนภาพเดียวกัน
- ในหน้าโมเดล กด **กลับมุมตรวจภาพ** หรือ **บันทึกภาพมุมนี้** เพื่อเก็บ PNG ของ renderer

คะแนน PSNR เทียบกับภาพอ้างอิงที่เตรียมไว้เสมอ แม้สลับไปดูภาพวิดีโอต้นฉบับ รุ่นเก่าใช้การเว้นมุมภาพ ส่วนรุ่นใหม่เว้นทุกมุมจากตำแหน่งที่เลือกไว้ทดสอบ จึงไม่ควรเทียบค่าเฉลี่ยข้ามวิธีแบ่งชุดโดยตรง COLMAP ยังใช้ภาพทั้งหมดเพื่อหา pose; นี่คือการเว้นตำแหน่งสำหรับการเทรน Gaussian

ชุดใหม่พยายามใช้จุดทดสอบบนกริดเวลาเดียวกันทุก 2 วินาทีเมื่อมีเฟรมนั้น ถ้าไม่มีหรือคลิปสั้นจะเลือกจากตำแหน่งที่มีจริงและบันทึก `evaluation_split.json` การปรับละเอียดต่อรักษาชุดทดสอบของรุ่นแม่ไว้

## ผลทดสอบจริง 15 ตุลาคม 2026

Windows / AMD Radeon RX 6700 XT / วิดีโอ DJI 8K:

| การทดสอบ | ผล |
| --- | --- |
| Pipeline 8 วินาที / 27 ตำแหน่ง / 216 Views | WGPU/Vulkan → COLMAP CPU → DirectML → Brush Vulkan → PLY/SPZ สำเร็จ |
| ชุดทดสอบแยกตำแหน่ง | เทรน 26 ตำแหน่ง ทดสอบ 1 ตำแหน่ง / 8 มุม; masked PSNR 27.532 dB |
| PNG 2048 + เก็บพื้นเพิ่ม / ชุดย่อย 6 ตำแหน่ง | เทรน 40 ภาพ ทดสอบ 8 ภาพ; masked PSNR 25.943 dB; พิกเซลใช้ประเมิน 88.62% |
| การคงรุ่นเดิม | checksum ของโมเดลก่อนหน้าตรงเดิมหลังสร้างรอบ PNG 2048 |

Regression ผ่าน Python 188 tests (รวม WGPU ฉายภาพจริงเทียบ CPU), JavaScript 13 ชุด และ HTTP บนแอปจริง 24 requests: หน้าเดิม/ใหม่, PNG ต้นฉบับ, Mask จริง และข้อมูลกล้องตรงมุมทั้ง PLY เต็ม/SPZ โมเดล DJI High เดิมมี SHA-256 ตรงกับก่อนพัฒนา Dependency check ผ่าน

ทั้งสองรอบใช้ 2,001 steps ในสคริปต์ทดสอบ ไม่เปลี่ยน production profile เป็นการยืนยันว่าเส้นทางทำงานได้ ไม่ใช่การทดลอง A/B ที่พิสูจน์ว่า 2048 คมกว่า เพราะชุดภาพและตำแหน่งทดสอบต่างกัน

## ตรวจผ่าน Chromium จริง

หลังผู้ใช้ระบุให้ลอง Chromium ได้ทดสอบด้วย Playwright 1.64.0 / Chromium 156.0.8078.4 ใน environment แยกจากแอป โดยใช้ profile ชั่วคราวและ RX 6700 XT ผ่าน ANGLE / Direct3D11 ไม่เริ่มงาน Train เพิ่ม

- เปิด Prepare, เปลี่ยนการเก็บพื้นและตัวเลือก PNG 2048, สลับภาพอ้างอิงต้นฉบับ, ซูม/เลื่อนภาพคู่ และลากเทียบได้
- High กับ Ultra ใช้ Source เดียวกัน มีภาพประเมินชื่อเดียวกัน 10 มุม รอบนี้เทียบ `frame_000408_view_00` ใน PLY เต็มและ SPZ รวม 4 แบบ เปิดที่ pose/FOV ของรุ่นนั้น และกดบันทึก PNG ผ่าน Browser ได้ครบ
- ไม่พบ JavaScript error หรือ HTTP error ในเส้นทางที่ตรวจ
- พบและแก้ภาพถูกตัดในโหมดพอดีหน้าจอ, Tutorial ล้นมือถือ และชื่อโมเดลทำให้หน้า Model ล้นมือถือ ตรวจซ้ำทั้ง 4 หน้าที่ความกว้าง 320 / 390 / 768 / 1440 px แล้วไม่ล้น
- ภาพ Full/SPZ ที่มุมนี้ใกล้เคียงกัน แต่ High และ Ultra ยังมีตัวอักษรบนกล่องที่เบลอ การตรวจหนึ่งมุมยังไม่ยืนยันคุณภาพทุกมุมหรือความคมที่เพิ่มขึ้นจาก Ultra

หลักฐานในเครื่อง: `web_data/capture_review/browser_chromium_20261015/REVIEW.md` พร้อมภาพก่อน/หลังและ PNG ที่ดาวน์โหลดจาก renderer ผล hardware ข้างต้นยังไม่ยืนยัน RTX/Ubuntu GPU และการทดสอบ viewport มือถือยังไม่ใช่การทดสอบบนโทรศัพท์จริง

## Progress ที่อัปเดตโดยไม่รบกวนการใช้งาน

- สถานะอัปเดตข้อความ/ความกว้าง progress ใน DOM เดิม ปุ่มดาวน์โหลดและลิงก์ไม่ถูกสร้างใหม่เมื่อข้อมูลยังเหมือนเดิม
- ระหว่าง hover หรือ focus บนรายการ, เปิดเมนู/รายละเอียด, เลือกข้อความ หรือใช้ dialog ระบบเก็บสถานะล่าสุดรอไว้ แถบ progress ยังอัปเดตได้ แล้วปรับข้อความหลังจบการใช้งานช่วงนั้น เพื่อไม่ให้แถวอื่นดันรายการที่กำลังชี้อยู่
- ภาพ/โมเดลใหม่แจ้งด้วยปุ่ม **โหลดรายการล่าสุด** โดยไม่มีการ reload ทั้งหน้าเอง หน้าบีบอัดใช้ API ตรวจสถานะ และหน้าผลทดสอบอัปเดต progress ของงานที่ติดตามได้ พร้อมปุ่มโหลดผลล่าสุด
- คำขอสถานะมี timeout และเก็บข้อมูลที่แสดงอยู่ไว้เมื่อเครือข่ายผิดพลาด

ทดสอบ Python 189 tests (ข้าม GPU opt-in 1 ข้อ), JavaScript 13 ชุด และ Chromium จำลองสถานะ API โดยไม่เริ่ม Train บน Dashboard / Jobs / รายละเอียด Job / Source Preview / Experiments / Compression ตรวจว่า hover, เมนู, dialog, ขอบเขตแถว และ scroll ไม่ถูกเปลี่ยนจาก polling หลักฐานอยู่ที่ `web_data/capture_review/stable_polling_20261015/review.json`

Ultra สำหรับ panorama ใช้ Views 1536 ตามค่าแนะนำ ส่วนเพดานภาพ Train 2048 ไม่ได้เพิ่มรายละเอียดที่ไม่มีอยู่ใน Views การเลือก PNG 2048 จะดึงภาพจาก Source ใหม่และมีจำนวนพิกเซลมากกว่า 1536 ประมาณ 78% แต่ยังไม่มีผล A/B ที่ควบคุมตัวแปรยืนยันว่าคมขึ้น จึงคง 1536 เป็นจุดเริ่มต้นได้
